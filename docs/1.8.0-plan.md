# Gryphon 1.8.0: plan

Status: **draft for Robin's decision.** Written 2026-11-14, just after 1.7.0 was published.
Nothing here is implemented. The one decision that gates everything else is in §2.

---

## 1. What 1.8.0 is for

Three things, in decreasing order of size:

1. **Reorganise the graph types** around what algorithms actually require, instead of around
   directed-versus-undirected. This is the breaking change and the reason for a new minor version.
2. **Fill the holes** the reorganisation makes visible anyway: `inDegree`/`outDegree`, a working
   `isConnected` for digraphs, and `GraphException` as an unchecked exception.
3. **Tidy-ups** that need a breaking release to land cleanly.

Under PVP — adopted in #32 — the first two numbers form the major version, so **1.8.0 is already a
major bump**. Calling it 2.0.0 would be signalling, not semantics. Either is defensible; 1.8.0 is
assumed throughout this document.

---

## 2. The decision: where preconditions live

Three options. A and B point in opposite directions; C is Robin's, and is the strongest form of A.

### Option A — push harder on types

Encode each precondition in the type system: capability or evidence parameters, so that
`MST.prim(digraph)` fails to compile.

### Option B — one `Graph` type, preconditions checked at the entry points

Collapse `DirectedGraph` and `UndirectedGraph` into one type. Direction becomes a property.
Every algorithm states its precondition and checks it on entry, through one mechanism and one
exception type.

### Option C — types in Scala, exceptions in the façade (Robin, 2026-11-14)

Each layer gets the strongest enforcement it can express: the Scala API rejects
`MST.prim(digraph)` at compile time, while the Java façade — which cannot express any of it —
checks at run time and throws, as it does today.

The honest encoding is a phantom type parameter:

```scala
sealed trait Orientation
sealed trait Undirected extends Orientation
sealed trait Directed   extends Orientation

final case class Graph[V, E, O <: Orientation](vertexMap: VertexMap[V])

def prim[V, E: {Zero, Ordering}](g: Graph[V, E, Undirected], start: V): ...
def kosaraju[V, E](g: Graph[V, E, Directed]): ...
```

Two practical notes: `Directed` and `Undirected` already exist as `EdgeType` values, so something
gets renamed; and every signature mentioning `Graph` gains a type parameter — invasive, but
mechanical.

**Where C beats B.** The predicate problem resolves more elegantly. Rather than making
`isConnected` total by redefining it as weak connectivity, the members that need undirectedness
simply do not exist without it:

```scala
extension [V, E](g: Graph[V, E, Undirected])
  def isConnected: Boolean = ...
  def degree(v: V): Int = ...
```

`degree` on a digraph becomes a compile error rather than a throw.

**Where C costs.** The façade must *manufacture* the evidence after its runtime check:

```scala
if !isUndirected then throw GraphException("prim requires an undirected graph")
MST.prim(g.asInstanceOf[Graph[V, E, Undirected]], start)
```

An unchecked cast in roughly twenty bridge methods. Not fatal, and close to what the bridge already
does by pattern-matching, but it means **the compile-time guarantee stops at the façade** — and the
façade is where both of 1.7.0's bugs were. Under B there is one check, shared by both layers; under
C there are two mechanisms either side of a boundary, free to drift.

**Worth facing squarely:** a weak version of C is what Gryphon has *today* — types on the Scala
side, a boolean and `IllegalStateException` in the façade, `JavaFacadeBridge` pattern-matching
between them — and the problems that prompted this plan are that arrangement's problems. That is not
decisive, because today's types are a *bad* A: `UndirectedGraph.addEdge` accepts any `Edge`, so they
prove nothing. A properly encoded C would be strictly better than the status quo. But it is the
arrangement with the track record here, and the record is not good.

### Recommendation: **Option B**, less strongly than before C was raised

Three reasons, strongest first.

**The type split does not enforce what it claims.** `UndirectedGraph.addEdge` has signature
`addEdge(edge: Edge[V, E]): UndirectedGraph[V, E]` — it accepts *any* `Edge`, so nothing prevents a
`DirectedEdge` entering an `UndirectedGraph`. The compile-time guarantee Option A would be
protecting does not currently exist at the one place that could establish it.

**Direction is already runtime data, in three places at once.** `Edge` declares
`def edgeType: EdgeType` on the base trait, with `Directed`, `Undirected` and `Undefined` as its
values; `VertexMap.+(pair: (V, V, EdgeType))` takes it as data; and the Java façade carries a
`boolean`. The graph-type split is a *fourth* encoding of the same fact, and the runtime one is
strictly more expressive — `Undefined` has no corresponding graph type.

**The `Graph` trait is already a union pretending to be a hierarchy.** Of its predicates,
`DirectedGraph` implements `isCyclic` and throws `UnsupportedOperationException` for `isConnected`
and `isBipartite`. An abstraction whose implementors answer "not applicable" to much of it is not
paying for itself.

A fourth, softer reason: Gryphon already tried Option A's mirror image. `core/DAG.scala` was a
`trait DAG[V, E] extends DirectedGraph[V, E]`, attempting to make *acyclicity* a type. Nothing
referenced it and nothing could — `DirectedGraph` is a case class, and no case class may extend
another — so it sat dead until it was deleted in 1.7.0.

### What Option B keeps from Option A

Not the types: the **explicit preconditions**. They exist today, scattered across three different
mechanisms. Option B gives them one vocabulary:

| Precondition | Required by |
|---|---|
| undirected | `MST.prim`, `Kruskal.mst`, `Boruvka.mst` |
| directed | `Kosaraju`, `TopologicalSort`, `BellmanFord`, `ShortestPaths.dijkstra` |
| acyclic | `AcyclicShortestPaths` |

One checking helper, one exception type, checked at the entry point, named in the Scaladoc.

### What decides between B and C

**Who writes Scala against Gryphon?** Compile-time safety is worth real complexity when people are
collecting compile errors from it. Today the only dependants are INFO6205 and DSAIPG — both Java,
both using three façade classes — so on the present evidence Option C buys safety nobody collects.
If a Scala audience is intended (CSYE7200, or Robin's own work), that changes the answer. This is
the one input the repository cannot supply.

**A middle path that keeps C open.** Do B in 1.8.0, and add a thin typed layer over it later if
Scala users materialise. Phantom types sit comfortably *on top of* a single runtime-checked `Graph`;
retrofitting a uniform runtime model *underneath* a type-heavy API is much harder. The ordering
costs little and keeps the option alive while the audience question is unresolved.

What to avoid is both at full strength in 1.8.0: two large changes whose interaction is the risky
part, in a release that already breaks compatibility.

### Prior art: what comparable libraries do

Not proof — none of these is a functional, immutable library, and Gryphon's purposes differ — but
worth knowing that the question has been settled several times before, and mostly the same way.

| Library | Where direction lives | Effectively |
|---|---|---|
| **Neo4j** (database) | every relationship is stored directed; queries choose whether to care | Option B, further than proposed |
| **Neo4j GDS** (algorithms) | an *orientation* on the projection: `NATURAL`, `REVERSE`, `UNDIRECTED`; algorithms declare which they accept and validation fails otherwise | Option B |
| **JGraphT** (JVM) | one `Graph<V,E>` interface plus a `GraphType` descriptor — `isDirected`, `isWeighted`, `isAllowingSelfLoops`, `isAllowingMultipleEdges`; algorithms interrogate it and throw | Option B |
| **NetworkX** (Python) | separate `Graph` / `DiGraph` / `MultiGraph` / `MultiDiGraph` classes — *and* `@not_implemented_for('directed')` decorators | the split, with run-time checks anyway |
| **Boost Graph Library** (C++) | `graph_traits<G>::directed_category` as a compile-time tag, algorithms constrained by concepts | Option A |

Three things follow.

**The two closest in purpose to Gryphon's algorithm layer — GDS and JGraphT — both chose Option B
independently.** Each runs the same family of algorithms over a user-supplied graph and each
validates preconditions at the entry point rather than in the type system.

**NetworkX is the cautionary one.** It is closest to Gryphon today: it has the type split *and*
still guards its algorithms with run-time decorators, because the split does not do the enforcement
work. That is the same conclusion reached above from `UndirectedGraph.addEdge` accepting any `Edge`.

**Boost shows Option A is achievable** — in a language with templates and concepts built for it, and
at a famous cost in approachability. That cost runs directly against Gryphon being a teaching
library.

**JGraphT also suggests a widening.** Its descriptor records more than direction: self-loops and
multi-edges are capabilities too. Gryphon can count self-loops (`numberOfSelfLoops`) but has no
notion of whether they are *permitted*. If a capability descriptor is being introduced, it may as
well have room for these.

*Source note: the above is from knowledge current to roughly May 2026, not from reading today's
documentation. The design points have been stable for years, but confirm the GDS orientation names
against current docs before relying on the detail.*

## 3. What changes, concretely

Assuming Option B.

| Today | After |
|---|---|
| `DirectedGraph[V, E]`, `UndirectedGraph[V, E]` | one concrete graph type; direction is a property |
| `graph.isConnected` throws on a digraph | `isConnected` means weakly connected, for all graphs |
| — | `isStronglyConnected`, beside it |
| `degree` undirected-only; no in/out variants | `degree` undirected-only; `inDegree`/`outDegree` for all |
| `isBipartite` throws on a digraph | defined for all (a digraph's underlying undirected graph) |
| preconditions: a type, a throw, and a boolean | one mechanism, one exception type |

**Not** collapsing: `DirectedEdge` and `UndirectedEdge`. They differ in meaning —
`from`/`to` against the symmetric `white`/`black` — and both already implement the common `Edge`
interface that carries `edgeType`. The edge level is where the distinction is real.

### Orientation as a view, borrowed from GDS

Worth considering alongside the above, because it subsumes something Gryphon currently does by hand.

If orientation is a property of *how an algorithm reads* a graph rather than of the graph itself —
GDS's `NATURAL` / `REVERSE` / `UNDIRECTED` — then two things fall out:

- `DirectedGraph.reverse` currently materialises an entire reversed graph, and Kosaraju's first pass
  runs over the copy. With orientation as a view, `reverse` becomes free, and Kosaraju's two passes
  become the same traversal read at two orientations.
- "Treat this digraph as undirected", which is what weak connectivity needs, stops being a special
  case and becomes one more orientation.

This is additive to Option B rather than an alternative to it, and could be deferred. It is listed
as open question 6.

## 4. Ramifications

### 4.1 Downstream consumers — smaller than it looks

The only projects depending on Gryphon are **INFO6205** and **DSAIPG**, and both:

- pin **gryphon_3 1.3.0** — four releases behind, so they have already skipped 1.4 through 1.7;
- consume it through **one file each** (`Tunnels_Gryphon.java`);
- import exactly three façade classes: `MinimumSpanningTree`, `WeightedEdge`, `WeightedGraph`;
- are **Java**, so a Scala-side reorganisation is invisible to them as long as the façade holds.

So the blast radius of Option B is close to zero for the actual consumers, provided the Java façade's
signatures are preserved. That is a strong argument for doing it now rather than later.

**Separate problem, worth fixing while we are here:** both poms use
`<scope>system</scope>` with a `<systemPath>` into `${user.home}/.m2`. That is not a resolvable
dependency — a student cloning the repo gets a build that fails unless the exact jar is already in
their local repository. It should be an ordinary Central dependency. This is a change to those two
repositories, not to Gryphon.

### 4.2 Scala users

This is the real break: `DirectedGraph` and `UndirectedGraph` are the types users name. Needs a
migration table in the README, in the style of Comparer 2.0's.

### 4.3 MiMa and versioning

Expect a long `mimaBinaryIssueFilters` list — every removed or moved type. Each entry wants a comment
saying why it is safe, as the 1.7.0 ones did. `previousRelease` is now `1.7.0`, and the 1.7.0 filters
have been retired, so the list starts empty.

### 4.4 The Java façade

Mostly unaffected by design, but two things change for the better:

- The façade's runtime checks stop being a lossy translation of a Scala type distinction and become
  the same mechanism the Scala layer uses. Today the two layers disagree about what counts as a type
  error, which is how both of 1.7.0's bugs got in.
- `GraphException` should become **unchecked**. It extends `Exception`, so Java sees a checked
  exception that façade methods do not declare — meaning a Java caller *cannot compile* a
  `catch (GraphException e)` around `graph.degree(v)`. This was found when Javadoc was first enabled
  in 1.8.0's first commit. Changing its supertype is a binary break, so 1.8.0 is the moment.

### 4.5 Documentation

- README: migration table, rewritten examples, the predicates table in "Directionality constraints"
  revisited (it becomes much shorter).
- Both doc sets now build in CI (`sbt doc javaApiDoc`), and `javaApiDoc` runs with `-Xdoclint`, so
  broken doc comments fail the build rather than degrading quietly.
- Every Java example in the README should be pasted into a temporary test and run before release, as
  was done for 1.7.0. Three of them had drifted and nothing had noticed.

### 4.6 Tests

623 today. The predicate tests are the ones that will move most, since `isConnected` and
`isBipartite` change from throwing to answering on digraphs. The tests pinning those throws
(`GraphPropertiesTest`) are the ones to update first — they were written to catch exactly this kind
of change.

## 5. Items independent of the decision

These stand on their own and could land first, in any order:

1. **`inDegree` / `outDegree`** — additions; close part of the degree gap.
2. **Weak `isConnected` for digraphs** — `ConnectedComponents` already computes it.
3. **`isBipartite` for digraphs** — same treatment.
4. **`GraphException` unchecked** — breaking, but tiny, and makes the façade usable from a Java
   `catch`.

Doing 1–3 before the reorganisation would make the `UnsupportedOperationException` holes disappear
and shrink the diff of the main change.

---

## 6. Proposed order

1. The independent additions (§5.1–5.3), as one PR. No breaks.
2. `GraphException` unchecked (§5.4). One filter, one release note.
3. The reorganisation (§2–3), as its own PR, with the migration table.
4. README and doc pass; compile every example.
5. Release, then move `previousRelease` to 1.8.0 and refresh `gh-pages`.

## 7. Open questions for Robin

1. **Option A, B or C?** Everything below §2 assumes B.
2. **Is there a Scala audience for Gryphon?** This decides between B and C more than anything else
   in the document, and only Robin can answer it. The only current dependants are Java.
3. **1.8.0 or 2.0.0?** Semantically identical under PVP; 2.0.0 signals the size of the change more
   loudly.
4. **Does the one concrete graph type keep the name `Graph`?** That collides with the existing
   `Graph` trait, so either the trait is absorbed into it or the concrete type needs another name.
5. **Should INFO6205 and DSAIPG be moved off `system` scope and onto a current Gryphon** as part of
   this, or separately? They are a long way behind, and whoever upgrades them will meet 1.7.0's
   `GraphException` change at the same time.
6. **Orientation as a view (§3), in 1.8.0 or later?** It makes `reverse` free and simplifies
   Kosaraju, but it is a second idea on top of an already-large change.
7. **Should the capability descriptor cover more than direction** — self-loops and multi-edges, as
   JGraphT's `GraphType` does? Gryphon counts self-loops but has no notion of permitting them.
