# Gryphon 2.0.0: plan

Status: **built and merged.** Written 2026-11-14, just after 1.7.0 was published; Robin chose
**Option C** (§2) the same day, along with **2.0.0** as the version (§1) and **bringing in Cats**
(§4.7); the naming question that was to be settled before any code turned out to have nothing in
it (§3). Of the seven questions in §7, six are answered and one — the capability parameter — is
deferred. **§8 records what this design deliberately does not do**, and is the part worth reading
first if question 5 is ever taken up.

---

## 1. What 2.0.0 is for

Three things, in decreasing order of size:

1. **Make the graph types express what algorithms actually require**, with an orientation the
   compiler checks and constructors that cannot be fooled — rather than two case classes that
   claim a distinction and do not enforce it. This is the breaking change and the reason for a new
   minor version.
2. **Fill the holes** it makes visible: `inDegree`/`outDegree`, and `GraphException` as an unchecked
   exception so a Java caller can catch it.
3. **Tidy-ups** that need a breaking release to land cleanly.

**Why 2.0.0 rather than 1.8.0** (Robin, 2026-11-14). Under PVP — adopted in #32 — the first two
numbers form the major version, so 1.8.0 would have been just as much a major bump: sbt and
Coursier would treat the two identically. The choice is therefore signalling, and the signal is
worth sending, because the model itself changes rather than a corner of it. It also matches the
convention across the Phasmid libraries: Comparer went to 2.0.0 when it became Scala-3-only and
derivation-based, and TableParser likewise.

Practical consequences: none for MiMa, whose `previousRelease` stays `1.7.0`; none for the artifact
name, which remains `gryphon_3`; and the README's migration section becomes "Migrating from 1.x",
in Comparer 2.0's style.

## 2. The decision: where preconditions live

Three options. A and B point in opposite directions; C is Robin's, and is the strongest form of A.

### Option A — push harder on types

Encode each precondition in the type system: capability or evidence parameters, so that
`MST.prim(digraph)` fails to compile.

### Option B — one `Graph` type, preconditions checked at the entry points

Collapse `DirectedGraph` and `UndirectedGraph` into one type. Direction becomes a property.
Every algorithm states its precondition and checks it on entry, through one mechanism and one
exception type.

### Option C — types in Scala, exceptions in the façade (Robin, 2026-11-14)

Each layer gets the strongest enforcement it can express: the Scala API rejects
`MST.prim(digraph)` at compile time, while the Java façade — which cannot express any of it —
checks at run time and throws, as it does today.

The honest encoding is a phantom type parameter:

```scala
sealed trait Orientation
sealed trait Undirected extends Orientation
sealed trait Directed   extends Orientation

final case class Graph[V, E, O <: Orientation](vertexMap: VertexMap[V])

def prim[V, E: {Zero, Ordering}](g: Graph[V, E, Undirected], start: V): ...
def kosaraju[V, E](g: Graph[V, E, Directed]): ...
```

Two practical notes: `Directed` and `Undirected` already exist as `EdgeType` values, so something
gets renamed; and every signature mentioning `Graph` gains a type parameter — invasive, but
mechanical.

**Where C beats B.** The predicate problem resolves more elegantly. Rather than making
`isConnected` total by redefining it as weak connectivity, the members that need undirectedness
simply do not exist without it:

```scala
extension [V, E](g: Graph[V, E, Undirected])
  def isConnected: Boolean = ...
  def degree(v: V): Int = ...
```

`degree` on a digraph becomes a compile error rather than a throw.

**Where C costs.** The façade must *manufacture* the evidence after its runtime check:

```scala
if !isUndirected then throw GraphException("prim requires an undirected graph")
MST.prim(g.asInstanceOf[Graph[V, E, Undirected]], start)
```

An unchecked cast in roughly twenty bridge methods. Not fatal, and close to what the bridge already
does by pattern-matching, but it means **the compile-time guarantee stops at the façade** — and the
façade is where both of 1.7.0's bugs were. Under B there is one check, shared by both layers; under
C there are two mechanisms either side of a boundary, free to drift.

**Worth facing squarely:** a weak version of C is what Gryphon has *today* — types on the Scala
side, a boolean and `IllegalStateException` in the façade, `JavaFacadeBridge` pattern-matching
between them — and the problems that prompted this plan are that arrangement's problems. That is not
decisive, because today's types are a *bad* A: `UndirectedGraph.addEdge` accepts any `Edge`, so they
prove nothing. A properly encoded C would be strictly better than the status quo. But it is the
arrangement with the track record here, and the record is not good.

### Decision: **Option C** (Robin, 2026-11-14)

Gryphon is a **Scala** graph library. The Java façade exists so that INFO6205 and DSAIPG students
can use it; it is an accommodation, not the product. The design is meant to be enjoyable *in Scala*,
and the long-term ambition is that Gryphon and its siblings are of a standard Typelevel would adopt.

That settles the question this document had left open, and it settles it against the earlier
recommendation. The case for B rested on "the only dependants are Java, so compile-time safety buys
nothing anyone collects" — true about today's dependants, and beside the point if the Scala API *is*
the library. Under C the cost lands where it belongs: in roughly twenty façade bridge methods,
written once, in the layer that exists for other people's convenience, rather than in the API that
is the point of the project.

Two supporting observations:

- The design has been attempted about four times, and each attempt reached for types: two graph case
  classes, a `DAG` trait, an `EdgeType` discriminator. The pull is consistent; what has been missing
  is an encoding that actually holds (see below).
- Typelevel alignment pushes the same way. Its libraries are typed, principled and lawful, and a
  runtime-checked `Graph` would sit oddly in that company. See §4.7.

### Why the status quo has to change regardless

Three reasons. They argue against the design as it stands, not for B over C — C also discards it.

**The type split does not enforce what it claims.** `UndirectedGraph.addEdge` has signature
`addEdge(edge: Edge[V, E]): UndirectedGraph[V, E]` — it accepts *any* `Edge`, so nothing prevents a
`DirectedEdge` entering an `UndirectedGraph`. The compile-time guarantee Option A would be
protecting does not currently exist at the one place that could establish it.

**Direction is already runtime data, in three places at once.** `Edge` declares
`def edgeType: EdgeType` on the base trait, with `Directed`, `Undirected` and `Undefined` as its
values; `VertexMap.+(pair: (V, V, EdgeType))` takes it as data; and the Java façade carries a
`boolean`. The graph-type split is a *fourth* encoding of the same fact, and the runtime one is
strictly more expressive — `Undefined` has no corresponding graph type.

**The `Graph` trait is already a union pretending to be a hierarchy.** Of its predicates,
`DirectedGraph` implements `isCyclic` and throws `UnsupportedOperationException` for `isConnected`
and `isBipartite`. An abstraction whose implementors answer "not applicable" to much of it is not
paying for itself.

A fourth, softer reason: Gryphon already tried Option A's mirror image. `core/DAG.scala` was a
`trait DAG[V, E] extends DirectedGraph[V, E]`, attempting to make *acyclicity* a type. Nothing
referenced it and nothing could — `DirectedGraph` is a case class, and no case class may extend
another — so it sat dead until it was deleted in 1.7.0.

### The preconditions, whichever way they are enforced

| Precondition | Required by |
|---|---|
| undirected | `MST.prim`, `Kruskal.mst`, `Boruvka.mst` |
| directed | `Kosaraju`, `TopologicalSort`, `BellmanFord`, `ShortestPaths.dijkstra` |
| acyclic | `AcyclicShortestPaths` |

Under C the first two become type parameters. **Acyclicity does not**: it is a property of the
edges, not of the construction, so it cannot be established by a smart constructor without checking
the whole graph. `ShortestPaths.acyclic` keeps its runtime check and its `IllegalArgumentException`.
Attempting otherwise is what killed the `DAG` trait. Say so in the Scaladoc rather than leaving a
reader to wonder why one of the three preconditions is different.

### What C must get right: the smart constructors

This is the crux, and it is where the previous attempts came apart.

A phantom type is only worth having if it cannot lie. Today `UndirectedGraph.addEdge` accepts any
`Edge`, so an `UndirectedGraph` may contain a `DirectedEdge` and the type proves nothing. Under C
the same hole would make `Graph[V, E, Undirected]` a decoration.

So the orientation parameter must be established at construction and preserved by every operation
that returns a graph:

- `addEdge` on a `Graph[V, E, Undirected]` accepts `UndirectedEdge[V, E]` only, and likewise for
  directed. The edge types already exist; they simply are not used to constrain anything.
- Every builder, parser and `unit`-style copy method carries the parameter through rather than
  widening to `Orientation`.
- The only place an orientation is *asserted* rather than inferred is the façade boundary, which
  checks at run time and casts — one well-marked mechanism, in one file, with a comment saying why.

If that discipline holds, the type means something. If it does not, C is Option B with extra
ceremony, which is the worst of the three.

### Prior art: what comparable libraries do

Not proof — none of these is a functional, immutable library, and Gryphon's purposes differ — but
worth knowing that the question has been settled several times before, and mostly the same way.

| Library | Where direction lives | Effectively |
|---|---|---|
| **Neo4j** (database) | every relationship is stored directed; queries choose whether to care | Option B, further than proposed |
| **Neo4j GDS** (algorithms) | an *orientation* on the projection: `NATURAL`, `REVERSE`, `UNDIRECTED`; algorithms declare which they accept and validation fails otherwise | Option B |
| **JGraphT** (JVM) | one `Graph<V,E>` interface plus a `GraphType` descriptor — `isDirected`, `isWeighted`, `isAllowingSelfLoops`, `isAllowingMultipleEdges`; algorithms interrogate it and throw | Option B |
| **NetworkX** (Python) | separate `Graph` / `DiGraph` / `MultiGraph` / `MultiDiGraph` classes — *and* `@not_implemented_for('directed')` decorators | the split, with run-time checks anyway |
| **Boost Graph Library** (C++) | `graph_traits<G>::directed_category` as a compile-time tag, algorithms constrained by concepts | Option A |

Three things follow.

**The two closest in purpose to Gryphon's algorithm layer — GDS and JGraphT — both chose Option B
independently.** Each runs the same family of algorithms over a user-supplied graph and each
validates preconditions at the entry point rather than in the type system.

**NetworkX is the cautionary one.** It is closest to Gryphon today: it has the type split *and*
still guards its algorithms with run-time decorators, because the split does not do the enforcement
work. That is the same conclusion reached above from `UndirectedGraph.addEdge` accepting any `Edge`.

**Boost shows Option A is achievable** — in a language with templates and concepts built for it, and
at a famous cost in approachability. That cost runs directly against Gryphon being a teaching
library.

**JGraphT also suggests a widening.** Its descriptor records more than direction: self-loops and
multi-edges are capabilities too. Gryphon can count self-loops (`numberOfSelfLoops`) but has no
notion of whether they are *permitted*. If a capability descriptor is being introduced, it may as
well have room for these.

*Source note: the above is from knowledge current to roughly May 2026, not from reading today's
documentation. The design points have been stable for years, but confirm the GDS orientation names
against current docs before relying on the detail.*

## 3. What changes, concretely

> **Revised 2026-11-14, after auditing what the code already enforces.** This section first said
> Option C meant collapsing `DirectedGraph` and `UndirectedGraph` into one `Graph[V, E, O]` with a
> phantom orientation parameter. **That turns out not to be necessary, and the phantom parameter
> is not being added.** The audit is below; the original sketch is kept after it, since the naming
> work it prompted stands on its own.

### What the audit found

Of the ten algorithm entry points, **seven already rejected the wrong orientation at compile time**,
because they take the concrete class:

| Already enforced | Enforced nothing (took `Traversable[V]`) |
|---|---|
| `BellmanFord.shortestPaths`, `AcyclicShortestPaths.shortestPaths`, `Kosaraju.stronglyConnectedComponents`, `TopologicalSort.sort`, `TopologicalSort.traversal` — all `DirectedGraph` | `MST.prim` |
| `Kruskal.mst`, `Boruvka.mst` — both `UndirectedGraph` | `ShortestPaths.dijkstra` |
| | `ConnectedComponents.components` |

So §2's "the type split does not enforce what it claims" was true of `addEdge`, and **not** true of
the algorithms. `DirectedGraph` and `UndirectedGraph` already *are* the orientation types; a phantom
parameter would restate in a type parameter what the class already says, at the cost of touching
every signature in the library.

### What Option C therefore needed, and what was done

1. **Constrain construction** so the types cannot lie — `addEdge` takes the graph's own edge kind.
   Done, with the undirected builder's directed-edge `TODO` fixed alongside it.
2. **Tighten the two loose algorithms.** `MST.prim` now takes an `UndirectedGraph` and
   `ShortestPaths.dijkstra` a `DirectedGraph`, matching the other seven. Neither body needed
   changing — both just delegate — and no caller needed changing either, which says they were
   always being passed the right thing.
3. **Take the predicates off the shared trait.** `isConnected` and `isBipartite` were abstract on
   `Graph[V]` and implemented in `DirectedGraph` as `throw UnsupportedOperationException`. They now
   exist only on `UndirectedGraph`, so `digraph.isConnected` is a compile error. The façade checks
   and throws `GraphException` — the same exception as the degree family, where it used to be
   `UnsupportedOperationException`.

`ConnectedComponents.components` keeps `Traversable[V]` deliberately: weak connectivity is defined
for both orientations, and it is the recommended answer for a digraph.

That is Option C: compile-time enforcement in Scala, runtime checks in the façade. No new type
parameter, and the diff is three targeted changes rather than a rewrite.

### Still outstanding

`degree`, `maxDegree` and `meanDegree` live on `UndirectedGraph`, so Scala already rejects them on a
digraph. Nothing left to do there.

### The original sketch, for reference

Kept because the naming investigation it prompted is still useful, and because a future change —
multiple capabilities (open question 5), or orientation as a view (open question 4) — may want it.

| Today | After |
|---|---|
| `DirectedGraph[V, E]`, `UndirectedGraph[V, E]` as separate case classes | one `Graph[V, E, O <: Orientation]`; `Directed` and `Undirected` are phantom types |
| `addEdge` accepts any `Edge`, so the type proves nothing | `addEdge` accepts only the edge type matching `O` |
| `isConnected` / `isBipartite` throw on a digraph | extension methods on `Graph[V, E, Undirected]` — absent, not throwing, on a digraph |
| — | `isStronglyConnected` on `Graph[V, E, Directed]` |
| `degree` undirected-only, enforced by a cast in the bridge | `degree` on `Graph[V, E, Undirected]`; `inDegree`/`outDegree` for both |
| `MST.prim(digraph)` compiles and fails at run time | does not compile |
| preconditions: a type, a throw and a boolean | types in Scala; one runtime check and cast at the façade |

Type-parameter churn is the main cost: every signature mentioning `Graph` gains a parameter. It is
invasive but mechanical, and the compiler finds every site.

### Naming: settled, and there is nothing to rename

An earlier draft of this plan said `Directed` and `Undirected` could not be both the phantom types
and the existing `EdgeType` values, so one pair would have to be renamed. That was wrong. They are
`object`s, so they occupy the **term** namespace; a trait of the same name occupies the **type**
namespace, and the two coexist as a companion pair.

Better still, one name can serve both roles honestly:

```scala
sealed trait Orientation

sealed trait Directed extends Orientation
sealed trait Undirected extends Orientation

case object Directed extends Directed, EdgeType:
  def oneWay: Boolean = true

case object Undirected extends Undirected, EdgeType:
  def oneWay: Boolean = false
```

`Directed` is then a type for `Graph[V, E, Directed]` and a value for `edge.edgeType`, and the value
*is a member of* the type. That removes the duplication §2 complains about — direction encoded as
both a type and runtime data — by making them one concept at two levels, rather than two encodings
that can disagree.

Verified on 2026-11-14 by compiling it against this build (Scala 3.9.0): the term and type uses
coexist, and `prim(directedGraph)` fails with a type mismatch, which is the whole point.

One loose end: `Undefined`, the third `EdgeType`, has no orientation counterpart. It should stay a
value-only `EdgeType` — a graph with unknown orientation is not a useful static type — unless the
parser turns out to need otherwise.

**Not** collapsing: `DirectedEdge` and `UndirectedEdge`. They differ in meaning —
`from`/`to` against the symmetric `white`/`black` — and both already implement the common `Edge`
interface that carries `edgeType`. The edge level is where the distinction is real.

### Orientation as a view, borrowed from GDS

Worth considering alongside the above, because it subsumes something Gryphon currently does by hand.

If orientation is a property of *how an algorithm reads* a graph rather than of the graph itself —
GDS's `NATURAL` / `REVERSE` / `UNDIRECTED` — then two things fall out:

- `DirectedGraph.reverse` currently materialises an entire reversed graph, and Kosaraju's first pass
  runs over the copy. With orientation as a view, `reverse` becomes free, and Kosaraju's two passes
  become the same traversal read at two orientations.
- "Treat this digraph as undirected", which is what weak connectivity needs, stops being a special
  case and becomes one more orientation.

Under C this fits naturally: an orientation-changing view is a function
`Graph[V, E, Directed] => Graph[V, E, Directed]` for `REVERSE`, and
`Graph[V, E, Directed] => Graph[V, E, Undirected]` for the undirected reading — which is exactly
the signature weak connectivity wants, and it makes the widening explicit in the type rather than
hidden in an algorithm. Still additive, and still deferrable. Open question 4.

## 4. Ramifications

### 4.1 Downstream consumers — smaller than it looks

The only projects depending on Gryphon are **INFO6205** and **DSAIPG**, and both:

- pin **gryphon_3 1.3.0** — four releases behind, so they have already skipped 1.4 through 1.7;
- consume it through **one file each** (`Tunnels_Gryphon.java`);
- import exactly three façade classes: `MinimumSpanningTree`, `WeightedEdge`, `WeightedGraph`;
- are **Java**, so a Scala-side reorganisation is invisible to them as long as the façade holds.

So the blast radius is close to zero for the actual consumers, provided the façade's signatures are
preserved — which under C they are, since the façade keeps its runtime checks and its `boolean`.
That is a strong argument for doing this now rather than later. It also means the students are not
the constituency to design for here: they are insulated either way.

**Separate problem, worth fixing while we are here:** both poms use
`<scope>system</scope>` with a `<systemPath>` into `${user.home}/.m2`. That is not a resolvable
dependency — a student cloning the repo gets a build that fails unless the exact jar is already in
their local repository. It should be an ordinary Central dependency. This is a change to those two
repositories, not to Gryphon.

### 4.2 Scala users

This is the real break, and under C it is the audience that matters: `DirectedGraph` and
`UndirectedGraph` are the types users name, and they become `Graph[V, E, Directed]` and
`Graph[V, E, Undirected]`. Needs a migration table in the README, in the style of Comparer 2.0's.

The good news for migration is that most call sites change in one mechanical way — a type name
becomes a type name with a parameter — and the compiler finds all of them. The exceptions are code
that was *relying* on the laxity: anything adding a `DirectedEdge` to an `UndirectedGraph`, or
holding a graph at the `Graph[V]` supertype, now has to say which orientation it means.

### 4.3 MiMa and versioning

Expect a long `mimaBinaryIssueFilters` list — every removed or moved type. Each entry wants a comment
saying why it is safe, as the 1.7.0 ones did. `previousRelease` is now `1.7.0`, and the 1.7.0 filters
have been retired, so the list starts empty.

### 4.4 The Java façade

Unaffected in signature, by design: `Graph<V>`, `WeightedGraph<V,E>` and the algorithm classes keep
their shapes, their `boolean` and their `IllegalStateException`.

What changes is `JavaFacadeBridge`, which becomes the single place where a runtime check mints
compile-time evidence:

```scala
if !isUndirected then throw GraphException("prim requires an undirected graph")
MST.prim(g.asInstanceOf[Graph[V, E, Undirected]], start)
```

About twenty such methods. Two things make that acceptable rather than alarming: it is confined to
one file, and it is close to what the bridge already does by pattern-matching. One thing makes it
worth watching: **this is where both of 1.7.0's bugs were**, so each cast wants a check next to it
that genuinely establishes what the cast asserts, and a test that exercises the failing direction.
The existing `GraphPropertiesTest` pattern — one test that the wrong orientation is refused, one
that the right one works — is the model.

Also:

- `GraphException` should become **unchecked**. It extends `Exception`, so Java sees a checked
  exception that façade methods do not declare — meaning a Java caller *cannot compile* a
  `catch (GraphException e)` around `graph.degree(v)`. This was found when Javadoc was first enabled
  on the 2.0.0 branch's first commit. **Done**, and it turned out not to be a binary break at all:
  an earlier draft of this plan said changing the supertype would be one, but `RuntimeException`
  *extends* `Exception`, so nothing is removed from the supertype set — a type is inserted into it.
  MiMa passes with no filter, existing bytecode that catches `GraphException` or `Exception` still
  works, and the only effect on Java source is to permit `catch` clauses that previously would not
  compile. Strictly an improvement, and it could have shipped in a patch release.

### 4.5 Documentation

- README: migration table, rewritten examples, the predicates table in "Directionality constraints"
  revisited (it becomes much shorter).
- Both doc sets now build in CI (`sbt doc javaApiDoc`), and `javaApiDoc` runs with `-Xdoclint`, so
  broken doc comments fail the build rather than degrading quietly.
- Every Java example in the README should be pasted into a temporary test and run before release, as
  was done for 1.7.0. Three of them had drifted and nothing had noticed.

### 4.6 Tests

623 today. The predicate tests are the ones that will move most, since `isConnected` and
`isBipartite` change from throwing to answering on digraphs. The tests pinning those throws
(`GraphPropertiesTest`) are the ones to update first — they were written to catch exactly this kind
of change.

### 4.7 Typelevel alignment

The stated ambition is that Gryphon and its siblings reach a standard Typelevel would adopt. That
is a long game, but it has one concrete implication that bears on 2.0.0, and several that do not.

**The one that bears on it: the typeclasses are home-grown.** Gryphon's algorithms are constrained
by `com.phasmidsoftware.visitor.core.Monoid`, `Zero` and the standard-library `Ordering`. A
Typelevel library would be expected to use `cats.kernel.Monoid`, `cats.kernel.Order` and
`cats.kernel.Semigroup` — the same abstractions, with laws, instances for the standard types, and
interoperability with everything else in that ecosystem. Nothing about Gryphon's algorithms needs
the bespoke versions; `BellmanFord` wants exactly `Monoid` and `Order`.

**Decided: this happens in 2.0.0** (Robin, 2026-11-14). The reason Cats was avoided before was to
keep the dependency list short, which he now judges a false economy. Two things support that:

- **`cats-kernel` is not clutter.** It is the small module holding `Eq`, `Order`, `Semigroup` and
  `Monoid`, and it has no transitive dependencies of its own. Gryphon does not need `cats-core`,
  `cats-effect` or anything else in the family to use them.
- **It costs one migration instead of two.** Doing it alongside the orientation change means users
  rewrite their call sites once.

**It is a Gryphon-only change** — checked on 2026-11-14, and smaller than this plan first assumed.
Visitor *defines* `Monoid` and `Zero`, but nothing in Visitor's own API demands them of callers:
they appear only in Gryphon's algorithm signatures, nine of them. So Gryphon can move to
`cats-kernel` without a coordinated Visitor release. Visitor can follow later, or not.

The mapping:

| Today | After | Status |
|---|---|---|
| `visitor.core.Monoid[A]` (`identity`, `combine`) | `cats.kernel.Monoid[A]` (`empty`, `combine`) — direct | **done** |
| `visitor.core.Zero[A]` (`identity` only) | `cats.kernel.Monoid[A]`, using only `empty` | **done** |
| `gryphon.util.HasZero[A]` | deleted — dead code, and its own comment said Cats was the answer | **done** |
| `scala.math.Ordering[A]` | `cats.kernel.Order[A]` | **deferred — open question 6** |

Two notes, both borne out. Cats has no identity-only class, deliberately — a lone identity has no
laws to satisfy — so `Zero` becomes `Monoid`, which slightly over-constrains Prim and Borůvka, both
of which compare but never accumulate. That is the lawful trade and the conventional one. And the
files importing `com.phasmidsoftware.visitor.core.{*, given}` did need narrowing, done with
`{Monoid as _, *, given}` in the three that use the wildcard *and* a Monoid.

**What the change actually cost, and gave back.** The import narrowing was three lines, not the
bulk of the diff. More interesting is what became redundant: `cats-kernel` supplies `Monoid[Double]`
through the implicit scope without an instance import, so four hand-written `Monoid[Double]`
instances in `JavaFacadeBridge` were deleted, and seven test files lost `import
com.phasmidsoftware.visitor.core.given_Monoid_Double` lines that `-Werror` then flagged as unused.
The dependency pays for itself immediately in code not written.

**`Ordering` was left alone, and the plan no longer assumes it changes.** Swapping it for
`cats.kernel.Order` is a different kind of change from the rest: `Ordering` is the standard
library's, not a home-grown class being retired, and requiring `Order` pushes work onto users, who
would need an `Order` instance for their own weight types where an `Ordering` does now. It is also
entangled with Visitor, whose priority queue takes an `Ordering`, so Gryphon would convert at the
boundary with `Order.toOrdering`. Typelevel convention says `Order`; the cost falls on callers. See
open question 6.

**The ones that do not bear on 2.0.0**, noted so they are not forgotten: `sbt-typelevel` as the
build plugin, cross-building for Scala.js and Native, property-based law testing via `discipline`,
and a code of conduct (already present). MiMa and the PVP scheme, adopted in 1.7.0, are already
part of that picture.

*Source note: as with §2's prior art, this reflects conventions as of roughly May 2026 and is not
from reading Typelevel's current guidance.*

## 5. Items independent of the decision

These stand on their own and could land first, in any order:

1. **`inDegree` / `outDegree`** — additions; close part of the degree gap.
2. **`GraphException` unchecked** — breaking, but tiny, and makes the façade usable from a Java
   `catch`.

Note what C removes from this list. Under B, weak `isConnected` and `isBipartite` for digraphs were
worth doing early, to close the `UnsupportedOperationException` holes. Under C those holes close
differently: the members stop existing on a digraph rather than answering for it, so adding digraph
implementations first would be work undone by the reorganisation. Leave them to it.

## 6. Proposed order

1. `inDegree` / `outDegree` (§5.1), as one small PR. No breaks.
2. `GraphException` unchecked (§5.2). One filter, one release note.
3. **The orientation parameter and its smart constructors** (§2–3), as its own PR. The constructors
   come first within it: until `addEdge` is constrained, the phantom type is decoration, and
   everything built on it would need revisiting.
4. The predicates as orientation-constrained extension methods, once the type holds.

## 8. What this design does not do

Recorded because it is the thing most likely to be rediscovered, and expensive to reconstruct.

The thinking this plan began from was that **a graph should be just a graph, required to prove
certain properties for particular algorithms**. What 2.0.0 actually ships is different: the property
and the representation are *fused*, because the class is the proof. `MST.prim` takes an
`UndirectedGraph`, and "being an `UndirectedGraph`" is simultaneously how the graph is represented
and the evidence that it is undirected.

That is pragmatic, it works, and it required almost no reorganisation — which is why it was chosen.
But it is not the same idea, and the difference shows in three places:

- **Acyclicity cannot be fused.** It is a property of the edges, not of construction, so no class
  can carry it. `ShortestPaths.acyclic` checks at run time and throws. So the library proves
  direction with types and acyclicity with a run-time check: two mechanisms for preconditions of
  the same kind. The "graph plus proofs" model would have treated both alike.
- **Properties cannot combine.** A second binary capability means four classes (see question 5).
  Evidence composes; class identity does not.
- **A property cannot be added without a new class**, nor proved about an existing value after the
  fact. There is no way to say "this `Graph` has been checked acyclic, here is the evidence" and
  have a signature demand it.

If the capability question (5) is ever taken up, this is the reasoning to revisit first: that work
is not an extension of what 2.0.0 did, but a move to the model 2.0.0 chose not to build.
